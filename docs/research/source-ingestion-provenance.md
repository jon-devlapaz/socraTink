# Source ingestion provenance architecture for Socratink

Date: 2026-07-31
Issue: [#16, Research provenance-preserving source ingestion and blob architecture](https://github.com/jon-devlapaz/socraTink/issues/16)
Scope: architecture research, not an implementation decision or database selection.

## Executive recommendation

Socratink should make **source evidence immutable, provenance explicit, and learner-facing knowledge claims interpretable rather than canonical source truth**. The first vertical proof should ingest one or two real source types, for example a YouTube transcript plus the source media metadata or a PDF plus OCR text, then prove that every downstream knowledge-map assertion can be traced back to immutable bytes, exact source spans, and the transformation activity that produced it.

The architecture should be organized around four layers:

1. **Evidence ledger**: immutable, content-addressed original blobs and metadata snapshots. Each captured byte sequence receives a digest, size, media type, source identity, retrieval context, and rights policy. Original blobs are never overwritten.
2. **Provenance graph**: every derivative is a separate entity generated by a named activity from one or more input entities, using W3C PROV concepts for `Entity`, `Activity`, `Agent`, `wasGeneratedBy`, `used`, `wasDerivedFrom`, attribution, bundles, invalidation, and version lineage.[^prov-overview][^prov-dm][^prov-o]
3. **Annotation and claim layer**: exact anchors to source material use W3C Web Annotation targets and selectors for text spans, byte or character ranges, image regions, audio/video time intervals, and code line ranges where applicable.[^annotation-model][^media-frags][^swhid] Extracted claims, clusters, mechanisms, summaries, and learner corrections are annotations or derived interpretation entities. They are not stored as if the source itself said them.
4. **Disposable projections**: chunk tables, vector indexes, search indexes, dashboards, graph layouts, and drill queues are rebuildable projections. They must point back to canonical entities and provenance but must not become canonical truth.

For the first vertical proof, adopt a minimal standards profile:

| Area | First-proof decision | Why |
|---|---|---|
| Content addressing | **Adopt** OCI-style descriptor fields, `mediaType`, `digest`, `size`, plus SHA-256 or stronger digests. Optionally expose `ni://` names later. | OCI descriptors are a compact operational pattern for content addressability and explicitly require media type, digest, and byte size.[^oci-descriptor] RFC 6920 standardizes hash-based names, but Socratink can defer `ni://` URI exposure.[^rfc6920] |
| Provenance | **Adopt** W3C PROV-DM as the conceptual model and PROV-O JSON-LD/RDF-compatible terms as the vocabulary. | PROV is purpose-built for entities, activities, agents, derivation, attribution, bundles, and validation constraints.[^prov-dm][^prov-o][^prov-constraints] |
| Exact anchoring | **Adopt** W3C Web Annotation Data Model selectors. | It directly models annotations targeting arbitrary resource segments, including timed multimedia segments.[^annotation-model] |
| Time and image fragments | **Adopt/adapt** Media Fragments URI `t=` and `xywh=` when targeting media and images. | W3C Media Fragments gives standardized temporal and spatial addressing across media.[^media-frags] |
| Time-coded transcript output | **Adapt** WebVTT for ASR/transcript cues when practical. | WebVTT is a W3C timed-text format for captions, subtitles, chapters, and time-aligned metadata.[^webvtt] |
| Archival packaging | **Adapt, not fully adopt** BagIt package structure for export and validation bundles, not every internal write path. | BagIt gives manifests and integrity checks for reliable storage and transfer, but full bagging per ingest event may be operationally heavy.[^bagit] |
| Preservation metadata | **Adapt** PREMIS entities and rights/events concepts into Socratink metadata. | PREMIS defines preservation Objects, Events, Rights, and Agents, which map well to fixity checks, rights, and preservation actions.[^premis-v3] |
| Research package context | **Adapt** RO-Crate JSON-LD for exportable research/evidence bundles. | RO-Crate describes datasets, data entities, software, people, organizations, and provenance actions using JSON-LD and schema.org terms.[^rocrate][^rocrate-prov] |
| OAIS | **Use as vocabulary only** for producer, submission package, archival package, dissemination package, representation information, and preservation planning. | OAIS is a reference model, not a software schema. It is useful for durable concepts, but too broad for a first vertical implementation.[^oais] |
| C2PA | **Reject for first proof, monitor later** unless Socratink ingests signed media credentials from publishers. | C2PA is valuable for tamper-evident media provenance and signatures, but it is an ecosystem and trust-list commitment that exceeds the first proof.[^c2pa] |
| IIIF | **Reject for first proof** unless image manuscript or scanned-page workflows become central. | IIIF search and annotation patterns are strong for cultural heritage image/text resources, but not necessary for transcripts and PDFs.[^iiif-search] |
| Database choice | **Reject premature choice**. | The epistemic contract can be expressed independently of relational, graph, object store, or content-addressed substrate. |

## Non-negotiable epistemic requirements

The database, object store, and graph engine are secondary. The core requirement is that Socratink can answer, for every learner-facing assertion:

1. **Which immutable source observation did this come from?**
   - A blob digest and size identify the exact bytes captured.
   - A source identity record identifies where the bytes came from, when they were captured, and which headers, API response metadata, or provider state were observed.
   - If a source is mutable, each capture is a new immutable version, not an update in place.

2. **Which exact part of the source supports it?**
   - A target selector identifies the span, timecode, image region, byte range, page/region, or code line range.
   - The selector should have enough redundancy to survive benign reformatting. For text, store both character offsets and quote context.

3. **Which transformation produced the interpretation?**
   - OCR, ASR, parsing, normalization, chunking, embedding, summarization, claim extraction, and knowledge-map synthesis are activities.
   - Activities record agent, model/tool identity, version, parameters, start/end time, input entity digests, output entity digests, and confidence or quality signals when available.

4. **What is asserted, and by whom?**
   - The source is an evidence object.
   - A claim is an interpretation generated by a model, tool, or learner, attributed to that actor and derivation activity.
   - The system must not collapse speaker claims, author claims, model summaries, and learner corrections into one untyped field.

5. **What changed later?**
   - New source versions, retractions, corrections, learner corrections, reprocessing, and metadata fixes are append-only events that supersede, invalidate, qualify, or conflict with earlier entities.
   - Deletion and rights events must be represented explicitly. Deleting access to a blob is different from deleting provenance metadata about why access was removed.

## Epistemic requirements versus storage implementation

Socratink should name an architecture contract before choosing storage.

### Epistemic contract

Canonical records are the minimum set needed to preserve truth-tracing:

- `SourceIdentity`: work-level identity, such as URL, DOI, repository, channel, creator, publisher, version label, and known external identifiers.
- `Capture`: retrieval event, request context, response metadata, capture timestamp, actor, and rights basis.
- `Blob`: immutable byte sequence, digest, digest algorithm, byte size, media type, encoding, filename if any, and storage locator.
- `Representation`: logical interpretation of a blob, such as PDF document, transcript, OCR text, ASR cue file, code file, image page, or normalized text.
- `Selector`: exact target inside a representation or blob.
- `Activity`: transformation or curation event.
- `Derivative`: output entity generated by an activity, such as OCR text, ASR transcript, parsed sections, chunks, embeddings, summaries, claims, knowledge map nodes.
- `Claim`: generated interpretation with support selectors, confidence, extraction activity, and possible conflicts.
- `PolicyEvent`: rights, erasure, embargo, license, consent, takedown, or retention decision.
- `CorrectionEvent`: learner correction, curator correction, source correction, retraction, or model reprocessing.

This contract can be implemented in multiple substrates.

### Storage implementation options

| Substrate | Strength | Weakness | Fit for first proof |
|---|---|---|---|
| Object store plus metadata DB | Excellent for immutable blobs and large derivatives. Operationally simple. | Does not answer graph lineage queries alone. Needs metadata discipline. | Strong default, but not a complete epistemic model. |
| Relational database | Strong consistency, constraints, migrations, provenance tables, transactional ingestion state. | Recursive lineage and multi-hop provenance queries can become awkward without careful schema design. | Best control plane for first proof if the team wants fast iteration. |
| RDF triple store or graph database | Natural fit for PROV-O, Web Annotation, RO-Crate, conflict relations, and lineage traversal. | Higher tooling and modeling cost. Can become schema-light without validation gates. | Useful later or as an export/query projection. Not required on day one. |
| Content-addressed store | Strong identity, dedupe, tamper detection, reproducible references. | Does not encode rights, source identity, or interpretation semantics by itself. | Adopt content addressing for blobs now. Do not make CAS the whole architecture. |
| Vector database | Good semantic retrieval over chunks and claims. | Embeddings are lossy, model-specific, and version-dependent. They cannot be canonical evidence. | Derived projection only. Rebuildable from canonical chunks and provenance. |

A defensible implementation could begin with object storage for blobs, a relational control plane for captures and activities, and JSON-LD export for provenance bundles. The key is that storage can change without changing the epistemic contract.

## Immutable original blobs and version lineage

### Blob identity

Every captured original and derivative byte sequence should be addressed by content digest and size. At minimum:

```json
{
  "digest": "sha256:...",
  "size": 1234567,
  "mediaType": "application/pdf",
  "createdAt": "2026-07-31T05:00:00Z",
  "storageLocator": "object://sources/sha256/...",
  "originalFilename": "lecture.pdf"
}
```

OCI content descriptors are a good operational precedent because a descriptor includes the type of content, a content identifier digest, and byte size, and recommends verifying retrieved content against digest and size.[^oci-descriptor] IANA/RFC media type registration gives the shared namespace for media type strings.[^rfc6838][^iana-media]

RFC 6920 can be adapted for externally portable hash names if Socratink later needs content-addressed identifiers that are themselves URIs. It defines Named Information identifiers such as `ni:///sha-256;...` for identifying digital objects by hash output.[^rfc6920] For a first proof, simple `sha256:<hex>` descriptors are easier to operate.

### Original immutability

Original blobs should be append-only:

- If the same source URL returns different bytes later, ingest a new `Blob` and a new `Capture`.
- If a title, license, or metadata field changes, record a metadata update event rather than mutating the capture record silently.
- If a parsing bug is fixed, generate new derivatives from the same original blob. Do not overwrite the old OCR, ASR, or chunk outputs.

### Version lineage

Use PROV for version lineage:

- A captured blob is a `prov:Entity`.
- A retrieval is a `prov:Activity` that `prov:generated` the blob and `prov:wasAssociatedWith` the retriever or service account.
- A normalized text file is a `prov:Entity` that `prov:wasDerivedFrom` the captured blob and `prov:wasGeneratedBy` a normalization activity.
- An entity that supersedes another can use PROV specialization, alternate, derivation, or invalidation depending on the semantics.[^prov-dm]

Distinguish these cases:

| Change type | Meaning | Suggested representation |
|---|---|---|
| New capture of same mutable URL | The source endpoint returned a new byte sequence. | New `Capture` and `Blob`, linked to same `SourceIdentity`; PROV derivation only if publisher declares it as a version. |
| Publisher version, edition, correction, or retraction | Scholarly record changed. | New work/version identity relation plus Crossref-style update relation when present. |
| Internal reprocessing | Socratink changed OCR, ASR, extraction, or chunking. | New derivative entity generated from same input by a new activity. |
| Metadata correction | Socratink corrected metadata about an entity. | Curation activity, possibly new metadata entity, old metadata retained or invalidated. |
| Rights deletion | Access must be removed or limited. | Policy event and tombstone, plus physical deletion or key destruction if required. |

For scholarly sources, Crossref Crossmark is relevant because it gives readers the current status of content, including corrections, retractions, and updates, and Crossref relationship metadata includes update relations and typed relations such as versions, replacements, derivations, supplements, and references.[^crossmark][^crossref-relations] Socratink should ingest these as external signals, not trust them as complete.

## Provenance model: adopt W3C PROV with a Socratink profile

W3C PROV defines provenance as information about entities, activities, and people involved in producing data or things, useful for assessing quality, reliability, and trustworthiness.[^prov-overview] PROV-DM is domain-agnostic and explicitly covers entities, activities, agents, derivation, attribution, bundles for provenance of provenance, specialization/alternate relations, and collections.[^prov-dm] PROV-O provides an OWL2 ontology for representing PROV in RDF and interoperable contexts.[^prov-o]

Socratink should adopt PROV conceptually and adapt it into a small profile:

### Core PROV mapping

| Socratink concept | PROV concept | Example |
|---|---|---|
| Original blob | `prov:Entity` | PDF bytes identified by SHA-256. |
| Retrieval/capture | `prov:Activity` | Download URL with headers at time T. |
| User, model, tool, API provider | `prov:Agent` | `yt-dlp 2026.x`, `whisper-large-v3`, `gpt-5.5`, learner account. |
| OCR output | `prov:Entity` | ALTO-like or plain text OCR derivative. |
| Claim extraction | `prov:Activity` | Prompt, model, temperature, schema, input chunk IDs. |
| Extracted claim | `prov:Entity` or Web Annotation body | Mechanism-level claim with support selectors. |
| Knowledge map | `prov:Entity` | Map generated from claims and source chunks. |
| Re-run with new prompt | New `prov:Activity` and output `prov:Entity` | Keeps both outputs comparable. |
| Correction | Curation `prov:Activity`, possible `prov:Invalidation` | Learner flags unsupported claim. |

### Bundles and provenance of provenance

PROV bundles matter because Socratink will sometimes import provenance from external systems and sometimes generate its own. Each provenance assertion should have its own source:

- Publisher metadata says a paper was retracted.
- Socratink capture service says it retrieved a PDF at a time.
- The OCR engine says it produced text with confidence scores.
- A learner says a claim is misleading.

The first proof can store this as simple `bundle_id` or `assertion_source` fields even if it does not operate a full RDF bundle store.

### Validation

PROV-CONSTRAINTS defines valid PROV instances as histories that are consistent and safe for logical reasoning and analysis.[^prov-constraints] Socratink should adapt this as ingestion validation, for example:

- every derivative must have at least one input entity and one generating activity;
- every activity must have an agent or tool identity;
- no canonical claim may lack at least one support selector or explicit `unsupported/generated` status;
- a derivative cannot claim to be generated before its input capture;
- invalidated entities remain queryable for audit but are excluded from current learner projections by default.

## Web Annotation selectors for exact source anchors

W3C Web Annotation models an annotation as a relationship between a body and a target, and its full model supports selecting arbitrary resource segments and timed multimedia segments.[^annotation-model] This fits Socratink because extracted claims and learner corrections are bodies about exact source targets.

### Selector profile

Socratink should adopt this selector profile:

| Source type | Selector strategy | Notes |
|---|---|---|
| Plain or normalized text | `TextPositionSelector` plus `TextQuoteSelector` | Offsets are precise. Quotes and prefix/suffix help recover after normalization. |
| PDF text | Page plus text position/quote in OCR or parsed representation, with optional region selector on page image | Raw PDF text offsets are brittle. Anchor to a derivative representation and preserve derivation to original PDF bytes. |
| Audio/video | `FragmentSelector` with Media Fragments `t=start,end`, plus transcript cue ID when available | Media Fragments standardizes temporal fragments.[^media-frags] |
| Image/scanned page | `FragmentSelector` with `xywh=` or `SvgSelector` for irregular regions | `xywh` is simple rectangles. SVG supports complex regions. |
| Byte stream | `DataPositionSelector` | Useful for exact byte ranges, compressed payloads, or binary extraction. |
| Code | SWHID with `lines=` qualifier when sourced from Software Heritage, otherwise file digest plus line/column selector | SWHIDs support content, directories, revisions, releases, snapshots, and optional line qualifiers.[^swhid] |
| Chunks | Store chunk boundaries as selectors over normalized text, not as canonical source | Chunks are projections and can be rebuilt. |

The key design is redundancy. A span anchor should include:

```json
{
  "sourceEntity": "sha256:source-or-representation",
  "selector": {
    "type": ["TextPositionSelector", "TextQuoteSelector"],
    "start": 18231,
    "end": 18402,
    "exact": "the quoted source text",
    "prefix": "text before",
    "suffix": "text after"
  },
  "representation": "normalized-text-v1",
  "representationWasDerivedFrom": "sha256:original"
}
```

For audio/video, preserve both the media time range and transcript range:

```json
{
  "target": {
    "source": "sha256:media-or-transcript",
    "selector": {
      "type": "FragmentSelector",
      "conformsTo": "http://www.w3.org/TR/media-frags/",
      "value": "t=372.4,389.8"
    }
  }
}
```

WebVTT is a practical derivative format for captions, subtitles, chapters, and time-aligned metadata.[^webvtt] Socratink does not need to adopt WebVTT as canonical truth. It can store WebVTT or equivalent cue records as ASR derivatives generated from media.

## Preservation/package standards

### BagIt

BagIt defines a filesystem layout for storage and transfer of arbitrary digital content. A bag encloses payload files and tag metadata, requires a payload manifest, and supports cryptographic-quality hash algorithms for integrity checking.[^bagit]

**Recommendation**: adapt BagIt for export, backup, import, and test fixture packages. Do not require every internal blob write to become a full BagIt directory.

First-proof BagIt-like export:

```text
source-ingest-bag/
  bagit.txt
  bag-info.txt
  manifest-sha256.txt
  tagmanifest-sha256.txt
  data/
    originals/<digest>.<ext>
    derivatives/<digest>.json
    provenance/prov.jsonld
    annotations/annotations.jsonld
    ro-crate-metadata.json
```

### PREMIS

PREMIS is the international preservation metadata standard for long-term usability of digital objects. PREMIS 3.0 is built on Objects, Events, Rights, and Agents.[^premis][^premis-v3]

**Recommendation**: adapt PREMIS concepts, especially:

- object characteristics: size, format, fixity, composition level;
- events: capture, fixity check, migration, normalization, validation, deletion, policy change;
- agents: software, humans, organizations;
- rights: license basis, permissions, restrictions, preservation exceptions, deletion requests.

Do not implement full PREMIS XML in the first proof. Use PREMIS-aligned fields and controlled terms where useful.

### OAIS

OAIS, the Open Archival Information System reference model, is a preservation reference model rather than a direct implementation schema.[^oais] Its most useful first-proof concepts are:

- **Producer**: source provider, learner, curator, API, or uploader.
- **Submission Information Package**: what is submitted or captured at ingest.
- **Archival Information Package**: preserved original plus preservation metadata and provenance.
- **Dissemination Information Package**: what Socratink serves to extraction, presentation, drill, or export.
- **Representation Information**: media type, encoding, parser assumptions, OCR/ASR model, and format profile needed to interpret bytes.
- **Preservation Description Information**: provenance, context, reference, fixity, and access rights.

**Recommendation**: use OAIS as design vocabulary only. Reject full OAIS process modeling for the first proof.

### RO-Crate

RO-Crate is a JSON-LD metadata specification for packaging research objects. It describes Data Entities such as files and datasets, recommends IANA media types via `encodingFormat`, and supports contextual entities such as people, organizations, software, and publications.[^rocrate][^rocrate-data] Its provenance section models equipment, software, create/update actions, inputs, outputs, agents, instruments, and action status.[^rocrate-prov]

**Recommendation**: adapt RO-Crate for exportable evidence bundles. A Socratink source bundle should be convertible to RO-Crate JSON-LD. This is valuable for interoperability and future research audits, but Socratink should not force every internal record to be native schema.org.

## Transformation and derivative lineage

Treat each transformation as a provenance-preserving activity. The original source is not a single pipeline input that disappears after extraction. It remains the root evidence object.

### Required transformation activities

| Stage | Input | Output | Required provenance |
|---|---|---|---|
| Capture | URL/API/upload/local file | Original blob plus capture metadata | request URL, redirects, response headers, content digest, size, media type, capture time, actor, rights basis. |
| Format sniffing | Original blob | media type/format assessment | tool name/version, detected type, confidence, mismatch flags. |
| OCR | PDF/image/page images | OCR text, page layout, confidence, page regions | OCR engine, version, language, page image digest, confidence, region mapping. |
| ASR | audio/video | transcript cues, timecodes, confidence | ASR model, version, segmentation, language, diarization, timestamps. |
| Parsing | PDF/text/HTML/transcript | sections, paragraphs, utterances, tables, code blocks | parser version, settings, structural assumptions. |
| Normalization | parsed text | canonical text representation | normalization rules, Unicode normalization, whitespace handling, redactions. |
| Chunking | normalized text | chunk entities | chunker version, boundaries as selectors, overlap policy, tokenization model. |
| Embedding | chunks/claims | embedding vectors | model name/version, dimensionality, input digest, preprocessing. |
| Summarization | chunks/sections | summaries | model, prompt, temperature, schema, support selectors. |
| Claim extraction | chunks/source spans | claim entities | model, prompt, schema, support selectors, confidence, uncertainty. |
| Knowledge-map synthesis | claims/source spans | clusters, relationships, drill nodes | extraction rules, support edges, model, prompt, validation status. |
| Learner correction | claim/map node | correction entity and optional revised claim | learner identity policy, rationale, target selector, supersession relation. |

### Derivative naming

Each derivative should be a named entity with its own content identity or structured ID. A derivative is not identified only by `(source_id, type)`, because the same source can have many OCR runs, chunking strategies, or extraction prompts.

Example derivative ID pattern:

```text
derivative:<activity_id>:<output_role>:sha256:<digest>
```

### Confidence and uncertainty

Confidence belongs to the activity output, not to the source. Examples:

- OCR confidence is confidence that OCR text matches the page image.
- ASR confidence is confidence that transcript tokens match audio.
- Claim extraction confidence is confidence that the claim is supported by selected spans.
- Learner confidence is confidence in their understanding, not confidence that the source is true.

## Extracted claims are interpretations, not source truth

Socratink's README says the graph should tell the truth by extracting structural knowledge maps from source material and turning them into a record of verified understanding. The ingestion architecture must preserve a sharper distinction:

- **Source observation**: immutable bytes and metadata captured from a source.
- **Source assertion**: what a speaker, author, or document appears to claim at a selected span.
- **Extractor interpretation**: what a model infers as a mechanism, cluster, premise, implication, or relationship.
- **Learner state**: what the learner currently understands, misunderstands, disputes, or corrects.
- **System projection**: what the dashboard, drill, or graph currently displays.

A knowledge-map node should therefore contain support edges, not just prose:

```json
{
  "type": "Claim",
  "claimText": "Threshold gating converts graded input into discrete frequency-coded output.",
  "claimRole": "mechanism",
  "generatedBy": "activity:claim-extraction-2026-07-31-001",
  "support": [
    {
      "target": "selector:text:...",
      "supportType": "direct_quote",
      "supportStrength": "strong"
    }
  ],
  "epistemicStatus": "model_interpretation",
  "confidence": 0.82
}
```

This prevents a common failure mode: a summary becomes untraceable and then gains unwarranted authority because it is stored beside original facts. In Socratink, the system should be able to show a learner: "this node is our interpretation of these exact source passages, produced by this model and later corrected by you."

## Conflicts, retractions, source identity, rights, deletion, and learner corrections

### Conflicts

Conflicts should be first-class relationships, not overwritten notes. A conflict can occur between:

- two source assertions;
- a source assertion and a later correction/retraction;
- two extractor interpretations;
- a learner correction and the system extraction;
- a source claim and trusted external evidence.

Represent conflict as an annotation or claim relation with support selectors on both sides. Do not resolve automatically unless a policy or curator makes a decision.

Suggested relations:

- `supports`
- `contradicts`
- `qualifies`
- `supersedes`
- `retracts`
- `corrects`
- `duplicates`
- `isVersionOf`
- `isDerivedFrom`

Crossref relationship metadata provides useful scholarly relationship names for version, replacement, derivation, supplements, references, and Crossmark update relations.[^crossref-relations] Use these where external metadata supplies them, but keep a Socratink-neutral relation model for non-scholarly sources.

### Retractions and updates

For scientific literature, Socratink should periodically refresh external metadata for DOIs and known scholarly identifiers. Crossmark is specifically designed to expose current status, including corrections, retractions, or updates to a research output, while warning that Crossmark presence is not a guarantee.[^crossmark]

First-proof behavior:

- Store `SourceIdentity` with DOI/URL and captured metadata.
- On refresh, record new metadata as a new entity.
- If Crossmark or relations indicate correction/retraction, add an update event and mark affected claims as `requires_review`.
- Do not delete old claims automatically. They may remain historically important but should be hidden or warned in current learning projections.

### Source identity

Source identity should be separated from blob identity:

- Blob identity answers: "which bytes?"
- Source identity answers: "which work, creator, edition, platform, repository, or publication?"
- Capture identity answers: "which observed retrieval event?"

This matters because the same bytes can be mirrored under many URLs, and the same URL can return different bytes over time.

Minimum identity fields:

- canonical URL if known;
- retrieval URL;
- DOI, PMID, arXiv ID, SWHID, ISBN, video ID, repository commit, or other external ID when available;
- title, creator, publisher/channel, publication date, version/edition;
- source platform and API endpoint;
- capture timestamp and response headers;
- content digest and size.

For code, SWHIDs are a strong external identity scheme because they name software artifacts using intrinsic object identifiers in a Merkle DAG and support qualifiers for origin, visit, anchor, path, and lines.[^swhid]

### Rights

Rights are not just UI labels. Rights determine whether Socratink can store, transform, quote, summarize, show to a learner, export, or share a source. PREMIS has a Rights entity in its preservation model.[^premis-v3] RO-Crate can record licenses on data entities.[^rocrate-data]

Minimum rights model:

- license or terms URL;
- rights basis, such as user upload, public web capture, open license, fair use analysis pending, platform API terms, institutional access, or explicit permission;
- permitted actions: store, transform, embed, quote, summarize, export, share;
- access restrictions and retention policy;
- takedown/deletion contact and status;
- rights review timestamp and reviewer/tool.

If rights are unknown, derivatives may be generated for private learner use only or quarantined until policy is decided.

### Deletion and erasure

Deletion is complex because immutable provenance conflicts with privacy and rights obligations. GDPR Article 17 gives data subjects a right to erasure under specified grounds and lists exceptions, including certain public interest, research, archiving, and legal claims contexts.[^gdpr17] Socratink should not encode legal conclusions in the architecture, but it must support policy outcomes.

Operational approach:

- Use append-only provenance for the fact that a deletion request was received and processed.
- Physically delete or cryptographically erase protected blobs where required.
- Preserve non-sensitive tombstones when legally permissible: digest, deletion event ID, reason category, and affected derivative IDs.
- Invalidate or quarantine derivatives generated from deleted or restricted sources.
- Rebuild vector/search/dashboard projections after deletion.

Do not assume content addressing makes deletion impossible. It means the system must separate immutable logical identity from physical retention and access policy.

### Learner corrections

Learner corrections are interpretations and should be recorded like any other provenance-bearing entity:

- target the specific claim, cluster, selector, or source span;
- include correction text and rationale;
- record learner identity according to product privacy policy;
- produce a new derived claim or mark an existing claim as disputed;
- trigger re-drill or review projections.

This preserves Socratink's learning value. A correction is not noise, it is evidence of a misconception repair or source interpretation improvement.

## Checksums, media types, capture metadata, and tamper evidence

### Checksums and fixity

Use digests at three levels:

1. **Blob digest**: digest over the exact stored bytes.
2. **Representation digest**: digest over normalized representation if normalization is used.
3. **Package or manifest digest**: digest over exported metadata and payload manifests.

BagIt supports cryptographic-quality hash algorithms and payload/tag manifests for integrity assurance in storage and transfer.[^bagit] HTTP Digest Fields define `Content-Digest` and `Repr-Digest` for integrity digests over HTTP content and representations, useful when capture sources provide or accept them.[^rfc9530]

At ingest:

- compute SHA-256 for every byte stream;
- record any provider-supplied digest, ETag, last-modified, content-length, and digest fields;
- verify content length and digest where available;
- run periodic fixity checks for stored blobs;
- record each fixity check as a preservation event.

### Media types and format identification

Media type should be recorded as both observed and detected:

- HTTP `Content-Type` or upload-provided media type;
- IANA media type where known;
- detected format from a tool such as file signature/sniffer;
- parser profile, encoding, character set, compression, and container details.

RFC 6838 defines media type specification and registration procedures, while IANA maintains the media type registry.[^rfc6838][^iana-media] RO-Crate recommends `encodingFormat` for file data entities, commonly using IANA media types.[^rocrate-data]

### Capture metadata

Minimum capture metadata:

- capture timestamp in UTC;
- actor or service account;
- source URL and final URL after redirects;
- request method, relevant headers, API parameters, and authentication category without secrets;
- response status, headers, content length, content type, digest fields, ETag, last-modified;
- platform-specific IDs, such as video ID or transcript language;
- tool name/version and environment;
- rights basis at capture time;
- failure/retry log if relevant.

### Tamper evidence

Content addressing detects byte changes but does not by itself prove who captured the bytes or when. For first proof:

- use cryptographic digests and append-only provenance records;
- keep audit logs for capture and transformation activities;
- optionally sign export manifests or provenance bundles later.

C2PA provides a standardized architecture for content provenance and authenticity, including manifests, assertions, signatures, validation, and binding to content.[^c2pa] It is relevant if Socratink ingests media with existing C2PA manifests or needs publisher-grade tamper evidence. It is too large for the first vertical proof unless signed media provenance is a core product requirement.

## Vector and chunk indexes are disposable projections

Chunks, embeddings, search indexes, and graph layouts should be treated as derived projections with provenance. They are operationally useful but epistemically lossy.

Rules:

1. A chunk is a derivative entity with selectors over a canonical representation.
2. An embedding is generated from a specific chunk by a specific model version and preprocessing pipeline.
3. A vector index contains embeddings and pointers. It is not a source of truth.
4. Search results must resolve back to chunks, selectors, claims, and original blob lineage.
5. Rebuilding the vector index must not change canonical provenance or claims, though it may change retrieval ranking.
6. Deletion, rights restrictions, retractions, and learner corrections must invalidate or filter projections.

This matters because a vector hit can be semantically near but evidentially wrong. The learner should see source-backed claims, not embedding-nearest guesses.

## First vertical proof architecture

### Target outcome

Prove this query:

> For any displayed knowledge-map node, show the original captured bytes, exact source span or time interval, all derivative transformations, extraction prompt/model/tool, confidence, conflict/retraction status, rights status, and learner corrections.

### Suggested first source types

Pick one pair:

1. **YouTube/transcript path**
   - original source identity: video URL, video ID, channel, title, capture timestamp;
   - captured transcript response or local transcript bytes;
   - optional media metadata capture;
   - normalized transcript;
   - time-coded cues if available;
   - chunks, extracted claims, knowledge map nodes.

2. **PDF/OCR path**
   - original PDF bytes;
   - page images or parsed text derivatives;
   - OCR text with page and region selectors;
   - normalized text;
   - chunks, extracted claims, knowledge map nodes.

The YouTube/transcript path aligns with current tooling in `tools/get_transcript.py`, but the PDF/OCR path better stress-tests regions and OCR lineage. If only one path can be built, choose transcript plus timecodes because it directly supports Socratink's existing extraction workflow.

### Minimal schema sketch

```text
source_identities
captures
blobs
representations
actions
entities
entity_derivations
selectors
annotations
claims
claim_supports
rights_events
correction_events
projection_indexes
```

Important invariant: `projection_indexes` can be dropped and rebuilt. `blobs`, `captures`, `actions`, `selectors`, `claims`, and policy/correction events cannot be silently rewritten.

### Minimal JSON-LD export

The first proof should export one `evidence-bundle.jsonld` containing:

- PROV entities/activities/agents;
- Web Annotation selectors and claim annotations;
- RO-Crate-like file/data entity metadata;
- BagIt-like manifest or digest list;
- rights and correction events.

This gives interoperability without forcing an RDF store internally.

## Standards adoption decisions

### Adopt

1. **W3C PROV-DM and PROV-O terms** for provenance.
   Use as the conceptual and JSON-LD/RDF-compatible vocabulary for lineage.

2. **W3C Web Annotation Data Model and Vocabulary** for claims, corrections, and exact source targets.
   It naturally represents body-target relationships and selectors.

3. **Media Fragments URI** for temporal and rectangular spatial fragments.
   Use `t=` for audio/video time intervals and `xywh=` for rectangular regions.

4. **IANA media types and RFC 6838 naming discipline**.
   Record media types and structured syntax suffixes consistently.

5. **SHA-256 or stronger digest descriptors with size and media type**.
   Use OCI descriptor structure as a simple operational pattern.

### Adapt

1. **BagIt**.
   Use for export, fixture, transfer, and archive validation packages. Do not make every internal ingest a BagIt filesystem tree.

2. **PREMIS**.
   Use Objects, Events, Agents, Rights, and fixity concepts. Do not implement full PREMIS XML yet.

3. **RO-Crate**.
   Use JSON-LD export shape for evidence bundles and research interoperability. Do not force all internal models into schema.org.

4. **WebVTT**.
   Use for ASR/caption derivatives and time-aligned metadata where available. Do not treat it as canonical if native transcript APIs provide better metadata.

5. **Crossref Crossmark and relation metadata**.
   Ingest as external scholarly update signals. Do not assume all sources have complete or correct Crossmark data.

6. **SWHID**.
   Use for code sourced from Software Heritage or when stable code line citation matters. For ordinary uploaded code snippets, a blob digest plus line selector is enough.

### Reject for the first vertical proof

1. **Full OAIS implementation**.
   Use vocabulary only. The reference model is too broad for first proof.

2. **Full PREMIS XML conformance**.
   Too much overhead before preservation workflows stabilize.

3. **C2PA signing and trust-list integration**.
   Valuable later for media authenticity, but premature unless signed media provenance is in scope.

4. **IIIF stack**.
   Strong for image/text cultural heritage objects, but not needed for the initial transcript/PDF source architecture.

5. **Native RDF graph database as an upfront requirement**.
   PROV-O compatibility matters, but storage should remain replaceable until query patterns are proven.

6. **Vector database as canonical memory**.
   Embeddings are projections only.

## Operational risks and mitigations

| Risk | Failure mode | Mitigation |
|---|---|---|
| Mutable URLs | Same URL returns changed bytes, old claims become untraceable. | New capture and blob per byte sequence; source identity separate from blob identity. |
| Parser drift | New parser changes offsets and breaks citations. | Selectors target representation versions; store quote context and derivation to original. |
| OCR/ASR errors | Extracted claims are based on bad transcription. | Preserve confidence, page/time selectors, and allow learner/curator correction. |
| Summary hallucination | Model invents unsupported claim. | Claims require support selectors or explicit unsupported status. |
| Retractions missed | Learner studies obsolete or retracted material. | Refresh DOI/Crossmark/metadata signals; mark affected claims `requires_review`. |
| Rights violation | System stores or exports content without basis. | Rights event required at capture; restrict projections and exports by policy. |
| Deletion impossible | Immutable content conflicts with takedown or erasure. | Separate logical tombstones from physical retention; support purge/key destruction and projection rebuild. |
| Vector index treated as truth | Retrieval ranking becomes evidence. | Resolve all vector hits through canonical claim/support/provenance records. |
| Premature database choice | Implementation optimizes for one query style and loses provenance semantics. | Lock epistemic contract first, keep substrates replaceable. |

## Evidence gaps

1. **Source-type priority remains unclear**. The issue asks for architecture, but not whether the first proof should prioritize YouTube transcripts, PDFs, webpages, code, or mixed media. The recommendation assumes transcript/PDF because those match current Socratink inputs.
2. **Rights policy needs legal/product decisions**. The architecture can record rights and deletion events, but cannot decide fair use, retention, redistribution, or learner privacy policy.
3. **Selector robustness must be tested on real sources**. TextPosition plus TextQuote is defensible, but PDF extraction and transcript normalization can still shift offsets. A fixture suite should measure reattachment success after normalization changes.
4. **Retraction coverage is incomplete outside scholarly DOI ecosystems**. Crossmark helps for participating publishers, but videos, blogs, course notes, and repositories need source-specific update checks.
5. **C2PA relevance depends on media provenance requirements**. If Socratink ingests journalism, social media, or AI-generated media where authenticity claims matter, C2PA may need to move from rejected to adapted/adopted.
6. **Graph query workload is unknown**. The report avoids choosing a database because there is no observed workload for lineage, conflict, and learner-state queries yet.
7. **Canonical claim schema needs product validation**. The architecture distinguishes claims, interpretations, and learner states, but the exact status taxonomy should be tested against real learnops-extract outputs and drill corrections.
8. **Privacy model for learner corrections is unspecified**. Corrections can be valuable evidence, but whether they are private, shareable, anonymized, or exportable is a product/privacy decision.

## Acceptance checklist for implementation

A first vertical proof is complete only if it can demonstrate:

- [ ] Original captured bytes are immutable and addressable by digest, size, and media type.
- [ ] The same source URL can have multiple captures and versions without overwriting.
- [ ] OCR/ASR/parsing/normalization/chunking/summary/claim activities produce separate derivative entities with tool/model versions and parameters.
- [ ] Every displayed claim has at least one source selector or is explicitly marked unsupported/generated.
- [ ] Text, timecode, region, and code selectors are represented using the adopted selector profile.
- [ ] Learner corrections and source retractions create new events rather than mutating history silently.
- [ ] Rights and deletion events can remove or restrict access while retaining permissible tombstones and invalidating projections.
- [ ] Vector and chunk indexes can be dropped and rebuilt from canonical entities.
- [ ] The system can export a BagIt-like or RO-Crate-like evidence bundle with PROV and annotation JSON-LD.
